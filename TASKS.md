# Leadflow — этапы работ и задачи

Источник требований: [PRD.md](./PRD.md).

Выполненные задачи отмечены `[x]` после проверки результата. Неотмеченные задачи остаются планом и не описывают доступные функции.

## Приоритеты и порядок работы

- **P0 — обязательный минимум:** этапы 0–6, 8–9. Приёмка MVP не зависит от дополнительных функций.
- **P1 — при наличии времени:** этап 7. Требования выбранной функции выполняются полностью, включая обработку ошибок и проверки.
- **Будущий этап:** подключение обычного Telegram описывается в документе для сдачи; его реализация не входит в MVP.

Последовательность: 0 → 1 → 2 → 3 → 4 → 5 → 6 → 8 → 9. После этапа 2 можно независимо разрабатывать CRM и бота. Дополнительные функции этапа 7 добавляются после проверки обязательного сценария; затем повторяется затронутая часть приёмки этапа 8. Материалы для сдачи можно собирать по ходу работы, а завершить после проверки живого MVP.

## Этап 0. Основа проекта и выбранный стек — P0

Согласованный стек: React + TypeScript + Vite и Ant Design 6 для фронтенда; Django + Django REST Framework для API; PostgreSQL; Telegram-бот на aiogram. Основа бэкенда — [Cookiecutter Django](https://github.com/cookiecutter/cookiecutter-django). Фронтенд и бэкенд находятся в одном репозитории; локальное окружение запускается через Docker Compose.

Согласованный UI: светлая серая тема, белые поверхности со скруглением 20 px, чёрный основной текст, лаймовые основные кнопки с чёрными подписями и синие ссылки. Использовать системный шрифт и готовые компоненты Ant Design 6.6.5. Утверждённый макет и исходные визуальные референсы сохранены в [docs/design](docs/design/README.md); это материалы оформления, а не данные CRM. Общая тема задаётся в `frontend/src/theme.ts` через публичные токены и API компонентов; свои стили ограничиваются геометрией страницы и адаптацией. Поведение списка и карточки задано в [PRD](PRD.md#список-лидов).

Согласованное размещение: React SPA — Cloudflare Workers Static Assets; Django API и отдельный постоянно работающий процесс бота — два сервиса Railway; PostgreSQL — Supabase. Supabase используется как база данных: авторизацией и доступом к данным CRM управляет Django, фронтенд обращается к Django API. Django и бот используют общую серверную логику и одну базу.

**Проверенный результат перехода UI:** экран использует Ant Design 6.6.5, общую светлую тему и русскую локализацию. Четыре клиентских теста, ESLint и сборка проходят. В headless Chromium проверены и визуально осмотрены экраны на ширинах 375 и 1440 px: нет горизонтальной прокрутки, виден клавиатурный фокус. Проверены блокировка кнопки при загрузке, ошибка с подменой ответа и повторное подключение к настоящему API. У статуса проверены атрибуты live-region; проверка со скринридером не проводилась. Сборка выдаёт предупреждение о размере JS-файла: 661 КБ, 213 КБ после gzip.

**Готово, когда:** основа проекта запускается локально по README.md, React-фронтенд собирается и обращается к Django API, Django и бот используют одну PostgreSQL, данные переживают перезапуск; существующие документы сохранены. Бизнес-функции реализуются на следующих этапах.

**Проверенный результат этапа 0:** четыре локальных сервиса запускаются через Docker Compose; API и бот подключаются к одной PostgreSQL. Применены стартовые миграции, пройдены 14 серверных и 4 клиентских теста, проверки кода и сборка React в контейнере. Подключение фронтенда к API, ошибка и повторное подключение проверены в браузере на компьютере и ширине 375 px, включая клавиатурный фокус. Техническая запись сохранилась после удаления и повторного создания контейнеров с прежним томом; после проверки она удалена. Настоящий токен проверен через Telegram API, отдельный процесс long polling запущен; ответ `/start` проверен автоматическим тестом с подменой Telegram.

Результат этапа 0 не включает сбор заявок. Хранение лидов и постоянных черновиков, общие проверки и сохранение заявок относятся к этапу 2; CRM и сценарий заполнения бота — на этапах 3–5. Сейчас фронтенд содержит только экран проверки соединения. Схема и команды локальной работы описаны в README, параметры генерации — в `backend/generation.json`, зависимости закреплены lock-файлами. Для проверки фронтенда используется ESLint вместо инструмента из шаблона Vite, который мешал чистой установке зависимостей в Docker. Деплой выполняется после готовности обязательного сценария, без отдельного облачного тестового окружения.

## Этап 1. Подготовка и технические решения — P0

Зависит от этапа 0.

- [x] **1.1** Зафиксировать состав MVP: одно общее рабочее пространство, вход по демонстрационному паролю, список и просмотр лидов, ручное добавление, четыре исходных тега, фильтр по тегу и рабочий Telegram-бот.
- [x] **1.2** Подготовить схему размещения на Cloudflare Workers Static Assets, Railway и Supabase: адреса фронтенда и API, маршрутизацию запросов и близкие регионы API и базы. Определить работу Django-сессий между фронтендом и API, передачу cookie и CSRF-защиту, при необходимости — разрешённые CORS origins. Предусмотреть сохранение данных после перезапуска, доступ по публичной ссылке и обновление открытой CRM не позднее чем через 10 секунд после отправки заявки.
- [x] **1.3** Определить структуру модулей CRM, бота и общей логики в подготовленном проекте. Зафиксировать контракт передачи токена бота и хеша демонстрационного пароля через серверное окружение без публикации секретов в клиентском коде или репозитории. Чтение новых настроек относится к этапу 3, настройка облачного окружения — к этапу 9.
- [x] **1.4** Определить JSON-контракты API для React-фронтенда: вход и выход, получение лидов и тегов, просмотр лида и ручное создание. Определить внутренние операции работы с черновиком бота и подтверждения заявки. Зафиксировать формат ошибок проверки полей и ошибок сохранения.
- [x] **1.5** Определить идентификатор отдельной заявки и правила повторной отправки для бота и ручной формы: повтор одной операции возвращает ранее сохранённый результат, новое заполнение создаёт отдельный лид даже при совпадении данных.

**Готово, когда:** определены схема размещения на согласованных платформах, работа сессий между фронтендом и API, структура модулей, данные и контракты обязательных операций.

**Принятые технические решения:**

- Один публичный адрес Cloudflare отдаёт React SPA и передаёт `/api/*` в Django на Railway. Ответы API не кешируются; браузер использует относительные адреса API и cookie своего домена. CORS для CRM не нужен. Локально используется существующий прокси Vite.
- API и единственный процесс long polling бота размещаются в Railway Amsterdam (`europe-west4-drams3a`) без режима сна. PostgreSQL — Supabase Frankfurt (`eu-central-1`), подключение через session pooler с TLS. Лиды, черновики, результаты отправки и Django-сессии хранятся в PostgreSQL. Фактические адреса заполняются на этапе 9; шаблоны и правила прокси описаны в [техническом контракте](docs/contracts.md#deployment-and-trust-boundary).
- Вход использует Django-сессию в базе с абсолютным сроком 48 часов. Cookie: `Secure`, `HttpOnly`, `SameSite=Lax`, без общего `Domain`. Вход, выход и изменения защищены CSRF. Демонстрационный вход не даёт прав Django Admin. Настройки и поведение нескольких вкладок описаны в [контракте доступа](docs/contracts.md#session-and-csrf-contract); продуктовые правила — в [PRD](PRD.md#доступ-к-crm).
- Общая проверка и транзакционные операции принадлежат `backend/leadflow/crm/`. API и `backend/leadflow/bot/` вызывают их. Бот отдельно управляет диалогом и доставкой сообщений. Серверные переменные и границы модулей описаны в [контракте](docs/contracts.md#module-and-secret-boundaries).
- API передаёт даты в UTC; клиент отображает часовой пояс устройства. Список обновляется каждые 5 секунд и при возвращении во вкладку. Внешние JSON-контракты, внутренние операции бота и единый формат ошибок описаны в [docs/contracts.md](docs/contracts.md).
- Отдельное заполнение получает UUID операции. Повтор с тем же содержимым возвращает ранее сохранённого лида; изменённое содержимое для уже сохранённой операции отклоняется. База защищает от одновременных повторов. Сохранение лида и завершение черновика выполняются одной транзакцией.

Согласованные пограничные случаи закреплены в PRD: неизвестный результат сохранения, устаревшие кнопки бота, выход в другой вкладке, недоставленное подтверждение, время устройства и ответы на вопросы бота. [Сценарии проверки](docs/contracts.md#implementation-verification) выполняются при реализации соответствующих этапов.

**Проверенный результат этапа 1:** состав MVP и согласованное поведение закреплены в PRD; схема размещения, сессии, границы модулей, серверные переменные, JSON-контракты и операции бота описаны в docs/contracts.md. Проверены 7 JSON-примеров, 13 локальных ссылок и якорей, форматирование Markdown и итоговый diff. На момент завершения этапа 1 подготовлены решения; API заявок, модели лидов, вход, диалог сбора заявки и облачный деплой ещё не были реализованы. Настройки из будущего контракта не обозначают уже подключённые переменные окружения. Тесты приложения и браузерные сценарии на этом этапе не запускались.

**Проверенный результат этапа 2:** созданы модели и миграции лидов, упорядоченных контактов, тегов, пользователей и черновиков бота, подтверждений сохранения. Четыре системных тега добавлены миграцией и защищены от удаления через прикладные операции и ORM; в Django Admin доступны только для просмотра. Общие серверные проверки принимают международный телефон, email и Telegram @username или ссылку, отклоняют ошибочные значения и объединяют повторы контактов внутри заявки. Черновик не имеет срока истечения. Лид, контакты, теги, подтверждение сохранения и завершение черновика записываются одной транзакцией.

Пройден 101 серверный тест, включая независимые соединения PostgreSQL для одновременных подтверждений, конфликтующих повторов, отмены, начала заново и отката незавершённой отправки. Django check, проверка отсутствия незаписанных миграций, Ruff и проверка форматирования проходят. Миграции применены к локальной базе. В отдельном Compose-проекте с вымышленными данными проверены перезапуск PostgreSQL и повторное чтение из новых контейнеров API и бота: лиды, контакты, теги, активный черновик и подтверждения сохранились; повторы не создали дублей. Тестовое окружение удалено после проверки.

Это серверная основа: HTTP-маршруты заявок, формы CRM и обработчики заполнения в Telegram реализуются на этапах 3–5. Бот по-прежнему сообщает, что сбор заявок недоступен. Проверка живого пути Telegram → CRM и экранов относится к следующим этапам.

## Вне объёма MVP

Не включать в обязательные задачи регистрацию, личные кабинеты, роли сотрудников, назначение ответственных, несколько рабочих пространств, канбан, аналитические отчёты, вложения, ИИ-разбор свободных сообщений и реализацию подключения обычного Telegram. Статический макет и имитация поступления заявок не заменяют рабочую интеграцию.
